# FORMYLA — система автоматической генерации геометрических чертежей

## 1. Что это за система

FORMYLA — платформа для изучения планиметрии (ЕГЭ/олимпиады). Одна из функций —
**автоматическая генерация чертежа по тексту задачи**, включая **дополнительные
построения** (доп. построения рисуются пунктиром).

Конвейер генерации чертежа с доп. построением (режим `solver_aux`):

1. **base_planner** (Gemini) — строит ИСХОДНЫЙ чертёж только по условию
   (треугольник, стороны, высоты/медианы/биссектрисы, заданные в условии).
2. **solver** (DeepSeek v4-pro) — решает задачу и возвращает JSON, в котором
   поле `aux_constructions` содержит СПИСОК доп. построений (op + точки +
   цитата из решения).
3. **compile_solver_aux** (`services/aux_compiler.py`) — ДЕТЕРМИНИРОВАННО
   (без LLM) превращает список `aux_constructions` в план движка, используя
   закрытый словарь операций `services/aux_ops.py`.
4. **merge_base_aux** (`services/figure_plan_validator.py`) — склеивает исходный
   план и aux-план.
5. **geometric_engine** (`geometric_engine/engine.py` + `geom.py`) — исполняет
   построения и рендерит SVG (пунктир = aux).

Ключевой принцип: **что продиктовал solver (DeepSeek) — то и должно быть
нарисовано.** Детерминированный компилятор обязан перевести ВСЕ диктованные
построения без потерь.

## 2. Структура папки

- `*.svg` / `*.png` — готовые чертежи (aux) для проверки глазами.
  Имена `job_<id>`.
- `code/` — файлы исходного кода, которые нужно править:
  - `services__aux_compiler.py` — компилятор доп. построений (ГЛАВНЫЙ);
  - `services__aux_ops.py` — словарь разрешённых операций;
  - `services__solution_generator.py` — вызов solver + repair;
  - `services__base_normalizer.py` — нормализация исходного плана;
  - `services__llm_router.py` — маршрутизация LLM-провайдеров;
  - `services__figure_plan_validator.py` — валидация и merge;
  - `routes__figures_generator.py` — сам конвейер;
  - `geometric_engine__engine.py` — исполнение построений + рендер;
  - `geometric_engine__geom.py` — математика (точки/прямые/окружности);
  - `data__figures__solver_task.txt` — системный промпт solver'а.

## 3. Как читать `solution_json` (что продиктовал DeepSeek)

Каждый элемент `aux_constructions` имеет вид:
```json
{"op": "line_extension", "points": ["B","A"], "id": null,
 "quote": "Построим точку D на луче BA за точку A так, что AD = AM.",
 "step_no": 1, "purpose": "..."}
```

Разрешённые `op` (закрытый словарь в `services/aux_ops.py`):
`segment`, `line`, `ray`, `altitude`, `median`, `angle_bisector`,
`perpendicular_bisector`, `midpoint`, `point_on_line`, `parallel_through`,
`perpendicular_through`, `line_extension`, `circle_center_radius`,
`tangent_at_point`, `line_intersection`, `reflect_point`.

ВАЖНО: поле `id`/`foot_id` у DeepSeek часто `null`, а имя новой точки задаётся
только в тексте `quote` («точку D», «основание K», «в точке E»). Компилятор
обязан извлекать это имя из цитаты.

## 4. Известные ошибки (что надо починить)

### 4.1. job_5427 — «окружность не там» (вписанная окружность)
DeepSeek диктует классическую цепочку вписанной окружности:
биссектрисы → их пересечение O → перпендикуляры из O на стороны (основания =
точки касания) → окружность с центром O.

Проблема: точка касания вписанной окружности вычисляется функцией
`geom.incircle_touch_point(a, b, c)`, где **первый аргумент — ПРОТИВОЛЕЖАЩАЯ
вершина**, а `(b, c)` — концы стороны касания. Если компилятор передаёт
аргументы в порядке «(конец стороны, конец стороны, вершина)» вместо
«(вершина, конец, конец)», точка касания попадает НА ДРУГУЮ сторону → радиус
и окружность «уезжают». Проверить порядок `p1/p2/p3` в `incircle_touch`.

### 4.2. Точки касания не совпадают с `equal_segments_mark`
В исходном плане точка касания иногда объявляется как `point_on_segment` с
произвольным `ratio`, из-за чего равенства касательных
(`AC1 = AB1`, `BA1 = BC1`, `CA1 = CB1`) численно не выполняются, хотя на
чертеже ставятся отметки «равные отрезки». Нужно заменять такие точки на
нативный `incircle_touch`.

### 4.3. Потеря новых точек (UNRESOLVED_POINT:D/E/K)
DeepSeek описывает «продлим BA за A до точки D» / «…в точке E» / «основание K»
без заполнения `id`. Компилятор присваивал точке синтетическое имя
`aux_*_N`, и следующий шаг (например `segment [D, M]`) падал с
`UNRESOLVED_POINT`. Нужно извлекать имя из `quote`.

### 4.4. line_intersection с будущей точкой-результатом
Формат `line_intersection` от DeepSeek бывает `points:[M, E, A, B]`, где E —
ещё не существующая точка (результат пересечения), а первая прямая — это уже
построенная параллель через M. Компилятор должен резолвить первую прямую из
реестра параллельных линий, а не трактовать M–E как прямую.

### 4.5. line_extension с равенством длины («AD = AM»)
«Продлим BA за A так, что AD = AM» — это НЕ центральная симметрия (там
AD = AB), а точка на луче за A на расстоянии |AM|. Нужен примитив
`point_on_ray(origin, away_from, length_from)`.

### 4.6. Служебные подписи на чертеже
Точки с внутренним id `aux_foot_*` / `aux_*` не должны подписываться этим
id. Подписываются только «настоящие» имена (D, K, E, O, …) или ничего.

## 5. Окружение

- Python 3.12, Flask + SQLAlchemy + SQLite (`instance/formyla.db`).
- Движок — свой, без numpy: `geometric_engine/`.
- LLM: DeepSeek v4-pro (решатель), Gemini 3.7 Flash (планировщик),
  Claude Opus 4.8 (независимая проверка), всё через OdiRouter
  (OpenAI-compatible endpoint, ключ в `.env` — сюда НЕ включаем).
