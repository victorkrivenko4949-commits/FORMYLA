# Обновление FORMYLA без простоя (zero-downtime)

Цель: сайт `formyla.net` обновляется так, что пользователи не замечают деплоя —
ни минуты «сайт не работает», ни потери данных. Это стандартная схема,
которую используют все компании: **новый инстанс поднимается рядом со старым,
трафик переключается только когда новый готов, старый гасится плавно.**

## Почему раньше сайт «зависал» при обновлении

Gunicorn открывает порт сразу, а приложение загружается после: миграции,
сидеры банков задач, LaTeX-фиксы — всё это идёт до первого ответа.
Если в Render не задан Health Check Path, Render переключает трафик на новый
инстанс сразу после открытия порта — и запросы пользователей висят, пока
грузится приложение. Отсюда «минута не работает».

## Что даёт ноль простоя

1. **Health Check Path = `/healthz`** (Settings → Health Check Path).
   Render не переключает трафик, пока новый инстанс не ответит 200 на
   `/healthz`. Пока новый грузится — работает старый. `/healthz` не ходит
   в БД и отвечает мгновенно.
2. **Pre-Deploy Command = `flask db upgrade --directory alembic_migrations`**
   (Settings → Build & Deploy → Pre-Deploy Command). Миграции выполняются
   один раз до замены инстанса. Если миграция падает — деплой останавливается,
   старая версия продолжает работать.
3. **Платный Instance Type** (у нас Pro Plus). Только на платных тарифах
   Render держит старый инстанс живым, пока поднимается новый.
4. **`--graceful-timeout 30`** в startCommand: старый инстанс получает 30
   секунд на завершение текущих запросов перед выключением.

Всё это уже прописано в `render.yaml`, но сервис создан вручную через
Dashboard — **проверь, что пункты 1 и 2 заданы именно в настройках сервиса**
(render.yaml для таких сервисов не применяется автоматически).

## Данные отдельно от кода

| Что | Где лежит | Переживает деплой |
|---|---|---|
| Пользователи, попытки, XP, банк задач | PostgreSQL на Render (отдельный сервис `formyla-db`) | Да |
| Фото решений | Cloudflare R2 (`services/storage.py`) | Да, если заданы `R2_*` |
| Вложения чатов | R2, либо `static/uploads/` если R2 не настроен | Только с R2 |
| Код, шаблоны, статика | GitHub → образ деплоя | Пересобирается каждый раз |

Диск файловой системы на Render эфемерный: всё, что не в PostgreSQL и не в R2,
исчезает при каждом деплое. **Render Persistent Disk не использовать** —
диск может быть примонтирован только к одному инстансу, поэтому сервисы
с диском деплоятся С простоем (это прямо противоположно нашей цели).

Настройка R2 (один раз):
1. Cloudflare → R2 → Create bucket (например, `formyla-photos`).
2. R2 → Manage R2 API Tokens → создать токен с правами Edit на этот бакет.
3. Подключить публичный домен к бакету (например, `photos.formyla.net`).
4. В Render → Environment добавить: `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`,
   `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, `R2_PUBLIC_URL`.
5. После этого фото решений и вложения чатов автоматически уходят в R2.

## Правило миграций: expand → contract

Старая и новая версии кода работают одновременно в окне деплоя, поэтому:

- ДОБАВИТЬ колонку/таблицу — можно в одном релизе с кодом, который её
  использует (старый код просто не замечает новую колонку).
- УДАЛИТЬ или ПЕРЕИМЕНОВАТЬ колонку — только в два релиза:
  1. Сначала деплоим код, который перестал её использовать.
  2. Потом отдельный релиз с миграцией на удаление.
- Нельзя в одном релизе менять смысл существующей колонки.

## Процедура обновления

1. Тесты локально: `python -m pytest tests/ --tb=short -q`.
2. Пуш в `main` (Auto-Deploy выключен — прод не тронется).
3. Render Dashboard → сервис `srv-d73br5ffte5s73euc56g` →
   **Manual Deploy → Deploy latest commit**.
4. Ждём статус **Live**. Во время деплоя сайт работает на старой версии.
5. Проверка (см. также DEPLOY_CHECK.md):
   - `https://formyla.net/__version` — `commit` совпадает с запушенным;
   - футер главной — `build <хеш>` совпадает;
   - `https://formyla.net/healthz` — `{"status":"ok"}`.
6. Не деплоить в 00:00–00:10 — в это время срабатывают cron-задачи
   APScheduler (сброс стриков и т.п.), в окне деплоя они могут выполниться
   на обоих инстансах.

## Откат

Render → сервис → вкладка Events/Rollback → **Rollback** на предыдущий деплой.
Откат — это тот же zero-downtime деплой предыдущего образа. Важно: если
после неудачного релиза уже применилась миграция БД, откат кода возможен
только когда миграция обратно совместима (правило expand/contract выше).

## Что НЕ делать

- Не включать Persistent Disk на веб-сервисе (убивает zero-downtime).
- Не хранить пользовательские данные в файлах рядом с кодом.
- Не убирать `/healthz` и не заменять его на страницу, требующую БД.
- Не поднимать `--workers` выше 1 (APScheduler и комнаты звонков задвоятся).
- Не включать Auto-Deploy без отдельного решения — деплой остаётся ручным.
