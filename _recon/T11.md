## 2. Число и тип воркеров

`startCommand` в `render.yaml`:
```
gunicorn app:app --workers 1 --threads 4 --worker-class gthread --timeout 120
```

- Воркеров: **1** (явно `--workers 1`)
- Потоков: **4** (`--threads 4`, gthread worker)
- Тип воркера: **gthread** (многопоточный, 1 процесс + 4 потока)
- Gunicorn 23.0.0 (из `requirements.txt`)

Если бы `--workers` не был задан, Gunicorn по умолчанию запустил бы
`2 * CPU + 1 = 2 * 4 + 1 = 9` воркеров.  Текущая конфигурация с 1
воркером осознанная: избежать дублирования APScheduler и in-memory
состояния (WebSocket-комнаты).

## 4. Расчёт на 300 учеников

**Допущение об одновременности:** из 300 зарегистрированных учеников
одновременно активны **30** (10%).  Обоснование:
- Учебная платформа — пиковая нагрузка 2–3 часа в день (вечер).
- Среднее время сессии 15–20 минут.
- 300 учеников / 24 часа * 3 пиковых часа = 37.5 средних, округлено до 30.

### Слагаемое 1: Сессии и объекты пользователей

На каждого активного пользователя:
- Flask-сессия (cookie, ~4 KB) — хранится на клиенте, память сервера не тратит
- SQLAlchemy identity map: ~10 объектов × 2 KB = 20 KB
- `current_user` + `g`-объекты: ~5 KB

Итого на активного: ~25 KB.  На 30 активных: **~0.75 MB**.

### Слагаемое 2: Рендер страниц при одновременных запросах

4 gthread-потока могут одновременно обрабатывать 4 запроса.
На каждый запрос:
- Jinja2-рендер шаблона: 2–5 MB (буфер вывода + контекст)
- SQLAlchemy-сессия: ~1 MB
- Ответ: ~100–500 KB

Пиковая нагрузка 4 одновременных запроса: **~20 MB**.

### Слагаемое 3: Очередь построения чертежей

Построение чертежа использует DeepSeek API (внешний вызов, таймаут 90 сек).
Очередь в БД (`figure_build_jobs`).  Память тратится только на активную
генерацию (1 задача в фоне).  Загрузка SVG-ответа: ~50 KB.

Очередь: **~1 MB** (один активный чертёж в фоновом потоке).

### Итоговая оценка

| Слагаемое | Оценка (MB) |
|-----------|-------------|
| Базовое потребление (импорт + Flask + SQLAlchemy) | 200 |
| Сессии и объекты 30 активных пользователей | 1 |
| Рендер 4 одновременных страниц | 20 |
| Очередь чертежей (1 активный) | 1 |
| Запас на GC-фрагментацию и пики (50%) | 111 |
| **ИТОГО** | **~333 MB** |

## 5. Тяжёлые по памяти операции

### `.all()` без пагинации (риск O(N))

Из grep-выдачи:

| Файл | Строка | Запрос |
|------|--------|--------|
| app.py | 1028 | `FigureBuildJob.query...filter(...).all()` |
| app.py | 3323 | `TheoryBlock.query...order_by(...).all()` |
| app.py | 5404 | `AdaptiveTestResult.query.filter_by(user_id=...).all()` |
| app.py | 7349 | `AdaptiveTask.query...order_by(...).all()` |
| app.py | 8871 | `test.problems.all()` |
| app.py | 9478 | `OlympiadSecret.query...order_by(...).all()` |

Самые рискованные: `AdaptiveTask.query.all()` (строка 7349) — при 9000+
задач загружает все в память.  `AdaptiveTestResult.all()` (строка 5404) —
у одного пользователя может быть сотни результатов.

### Загрузка фото для Kimi

`app.py:5215–5230`:
```python
import base64
image_data = base64.b64encode(first_file.read()).decode('utf-8')
```

Фото загружается **целиком в память** через `.read()`, затем кодируется
в base64 (раздувает размер на 33%).  Ограничения на размер загружаемого
файла в коде не найдено — теоретически ученик может загрузить фото 50 MB,
которое превратится в 67 MB base64-строки в памяти.

### SVG / BytesIO

Прямых `BytesIO` в результатах grep не найдено.  Геометрический движок
использует `minidom` для построения SVG (умеренное потребление).

## 6. Вердикт

| Параметр | Значение |
|----------|----------|
| Доступно памяти (Pro Plus) | 8192 MB |
| Требуется при 300 учениках | **333 MB** |
| Хватает? | **ДА, с запасом 24x** |
| Узкое место | Не память, а отсутствие пагинации в `.all()` и загрузка фото целиком |

### Что менять (рекомендации, не обязательные для приёмки)

1. `app.py:7349` — заменить `.all()` на `.limit(100)` или пагинацию.
2. `app.py:5230` — добавить проверку `Content-Length` перед `file.read()`
   (например, максимум 10 MB).
3. `app.py:5404` — `.limit(50)` вместо `.all()` для истории тестов.

### Код не меняется

Часть 3 — только расчёт и чтение.
