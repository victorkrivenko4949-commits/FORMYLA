# Регламент выпуска гайдов и открыток ИИ-архитекторами ИТ-продуктов H2

**Версия:** v1.1
**Дата:** 2026-08-29
**Область:** любой ИТ-продукт H2, у которого есть ИИ-архитектор
**Аудитория:** ИИ-архитектор ИТ-продукта H2

---

## §1. Зачем регламент

У каждого ИТ-продукта H2 есть **два целевых читателя гайдов**:

- **Пользователь продукта** — ЛЛМ, которая запускает и использует продукт снаружи, не заходя внутрь его реализации.
- **ИИ-архитектор продукта** — ЛЛМ, которая знает продукт снаружи и внутри: проектирует, диагностирует, патчит и приёмит его. Может параллельно выступать и Пользователем продукта.

Обоим нужен **всегда актуальный, версионированный, машинно-читаемый гайд**. Прибитые `file_id` физического гайда протухают с первым же релизом. Регламент задаёт единый механизм публикации и открытия гайдов через **открытки-указатели** — файлы с постоянным именем в OWUI, внутри которых лежит актуальный `file_id` физического гайда.

## §2. Что должен произвести каждый ИИ-архитектор ИТ-продукта H2

Для своего продукта ИИ-архитектор обязан создать и поддерживать в OWUI **4 файла**:

| # | Тип | Имя (правила см. §3) | Аудитория |
|---|-----|----------------------|-----------|
| 1 | Физический Пользовательский гайд | версионное | Пользователь продукта (ЛЛМ) |
| 2 | Физический Архитекторский гайд | версионное | ИИ-архитектор продукта (ЛЛМ) |
| 3 | Открытка Пользовательского гайда | **постоянное** | Все клиенты (ЛЛМ и агенты) |
| 4 | Открытка Архитекторского гайда | **постоянное** | Все клиенты (ЛЛМ и агенты) |

## §3. Правила именования файлов

Регламент **не диктует конкретные имена** продуктов/агентов. Каждый ИИ-архитектор сам подставляет `<PRODUCT>` в шаблон исходя из своей области.

### §3.1. Шаблоны имён

| Файл | Шаблон имени |
|------|--------------|
| Физический Пользовательский гайд | `GUIDE_<PRODUCT>_v<N>_r<M>.md` |
| Физический Архитекторский гайд | `ARCHITECT_GUIDE_<PRODUCT>_v<N>_r<M>.md` (или `_v<N>.md`, если ревизии не используются) |
| Открытка Пользовательского гайда | `GUIDE_<PRODUCT>_ACTIVE.md` (без `_v…`, без `_r…`) |
| Открытка Архитекторского гайда | `ARCHITECT_GUIDE_<PRODUCT>_ACTIVE.md` |

### §3.2. Требования к `<PRODUCT>`

- Короткий однозначный идентификатор продукта.
- **Не менять** после первой публикации открытки — иначе клиенты перестанут её находить.
- Не совпадать между разными продуктами H2.
- Одинаковый `<PRODUCT>` в паре «физический гайд ↔ открытка» и в паре «Пользовательский ↔ Архитекторский» для одного продукта.

### §3.3. Правила версионирования физических гайдов

- **Мажорная версия `v<N>`** увеличивается при изменении контракта/семантики.
- **Ревизия `r<M>`** увеличивается при уточнениях без ломки контракта.
- **Дата выпуска** обязательна в теле физического гайда.
- **История версий** обязательна в физическом гайде: перечень всех предыдущих `v<N>_r<M>` + краткое описание изменений.

### §3.4. Постоянство имён открыток

Имена открыток **никогда не меняются** после первой публикации. Смена имени открытки = поломка всех клиентов, которые ищут её по прежнему имени.

## §4. Что должно быть внутри физического гайда

Регламент задаёт только два обязательных пункта:

1. В **обоих физических гайдах** — раздел «Как обновлять открытку» (§5).
2. В **Архитекторском физическом гайде** — раздел «Как открыть актуальный Пользовательский гайд через его открытку» (§6).

Остальное содержимое гайдов — на усмотрение ИИ-архитектора продукта.

## §5. Раздел «Как обновлять открытку» (шаблон для обоих гайдов)

Каждый физический гайд должен содержать раздел с этим точным содержимым (адаптированным под свой `POINTER_NAME`).

### §5.1. Гигиена «ровно 1 freshest»

В OWUI должна быть **ровно одна** копия открытки с данным именем. Если поиск `GET /api/v1/files/search?filename=<POINTER_NAME>` возвращает больше одного файла — предыдущий релиз сделан с нарушением, все старые копии подлежат удалению.

### §5.2. Что должно лежать внутри открытки

- `filename` физического гайда с версией.
- OWUI `file_id` физического гайда.
- SHA256 физического гайда.
- Размер в байтах.
- Дата выпуска.
- Ссылка вида `GET /api/v1/files/<file_id>/content`.
- Инструкция для клиентов (алгоритм чтения через search + freshest).
- Правило гигиены «ровно 1 freshest».
- Проверочный `curl` (одноразовая проверка).
- История версий.

### §5.3. Алгоритм выпуска новой версии

1. Собрать новый физический гайд (обновить `v<N>_r<M>`, дату, историю версий).
2. Посчитать `sha256sum` и размер в байтах.
3. Загрузить новый физический гайд через `POST /api/v1/files/` (multipart, поле `file`), с credential `custom-cred:chat.h2platform.ru`. Записать новый `file_id`.
4. Собрать новое содержимое открытки (новый `file_id`, SHA, размер, дата; расширить историю).
5. Загрузить обновлённую открытку через `POST /api/v1/files/`. Записать новый `file_id` открытки.
6. Проверить `GET /api/v1/files/search?filename=<POINTER_NAME>` → должно быть ≥ 1.
7. **Удалить ВСЕ старые копии открытки** через `DELETE /api/v1/files/{id}` (все кроме freshest по `created_at`).
8. **Удалить старый физический гайд** через `DELETE /api/v1/files/{old_id}`.
9. Повторно проверить `GET /api/v1/files/search?filename=<POINTER_NAME>` — должно вернуть **ровно 1**.
10. Провести roundtrip-проверку (§5.4): скачать физический гайд через открытку → сверить SHA с той, что записана в открытке.

### §5.4. Проверочный скрипт (roundtrip)

```bash
POINTER_NAME="<POINTER_NAME>"
BASE="https://chat.h2platform.ru"

# 1. search + freshest
POINTER_ID=$(curl -sk "$BASE/api/v1/files/search?filename=$POINTER_NAME" \
  | python3 -c "import json,sys; a=json.load(sys.stdin); a.sort(key=lambda x:x['created_at'], reverse=True); print(a[0]['id'])")

# 2. read pointer
POINTER_BODY=$(curl -sk "$BASE/api/v1/files/$POINTER_ID/content")

# 3. extract physical file_id + SHA
GUIDE_ID=$(echo "$POINTER_BODY" | grep -oP 'OWUI file_id:\*\* `\K[a-f0-9-]+' | head -1)
EXPECTED_SHA=$(echo "$POINTER_BODY" | grep -oP 'SHA256:\*\* `\K[a-f0-9]+' | head -1)

# 4. download physical and verify SHA
curl -sk "$BASE/api/v1/files/$GUIDE_ID/content" -o /tmp/g.md
ACTUAL_SHA=$(sha256sum /tmp/g.md | awk '{print $1}')
[ "$EXPECTED_SHA" = "$ACTUAL_SHA" ] && echo OK || echo MISMATCH
```

Все `curl` — с credential `custom-cred:chat.h2platform.ru`.

## §6. Раздел в Архитекторском гайде «Как открыть Пользовательский гайд через открытку»

В Архитекторском гайде обязательно должен быть раздел, объясняющий алгоритм чтения **Пользовательской открытки** — чтобы ИИ-архитектор мог программно достать актуальный Пользовательский гайд, не хардкодя `file_id`.

Минимальное содержимое раздела:

- **Ключевое правило:** открытка открывается **всегда по имени, никогда по прибитому `file_id`**.
- Алгоритм (одинаковый для обеих открыток, меняется только `POINTER_NAME`): search → freshest по `max(created_at)` → read pointer → extract physical `file_id` → download → опционально SHA roundtrip.
- Готовый пример (bash или PowerShell) с параметризованным `POINTER_NAME`.
- Указание, что тот же алгоритм применим к обеим открыткам продукта (Пользовательской и Архитекторской).
- Запреты:
  - Хардкодить `file_id` физического гайда в скрипты, PMA, напоминания.
  - Пропускать шаг «взять freshest по `max(created_at)`» при поиске.
  - Считать открытку отсутствующей после первой 404 без ретрая через 2 сек.

## §7. Кросс-ссылки между гайдами

- Пользовательский гайд должен указывать, что для того же продукта существует Архитекторский гайд с постоянной открыткой `ARCHITECT_GUIDE_<PRODUCT>_ACTIVE.md`.
- Архитекторский гайд обязан содержать §6 (алгоритм открытия Пользовательской открытки).

## §8. Проверка перед публикацией (чек-лист)

Каждый релиз считается принятым, только если ИИ-архитектор прошёл этот чек-лист:

- [ ] Оба физических гайда содержат корректную шапку (продукт, версия, дата).
- [ ] Оба физических гайда содержат раздел «Как обновлять открытку» (§5).
- [ ] Архитекторский гайд содержит §6 «Как открыть Пользовательский гайд через открытку».
- [ ] Оба физических гайда содержат обновлённую «Историю версий».
- [ ] Обе открытки содержат актуальные `file_id`, SHA256, размер, дату.
- [ ] `GET /api/v1/files/search?filename=<POINTER_NAME>` возвращает **ровно 1** файл для каждой открытки.
- [ ] Roundtrip-проверка (§5.4) для обеих открыток — PASS (SHA совпал).
- [ ] Старые физические гайды и старые копии открыток удалены через `DELETE /api/v1/files/{id}`.
- [ ] Имена файлов соответствуют шаблонам §3.1.

## §9. Общий контракт OWUI-API

- Базовый URL: `https://chat.h2platform.ru`
- Credential: `custom-cred:chat.h2platform.ru`
- Загрузка: `POST /api/v1/files/` (multipart, поле `file`)
- Чтение содержимого: `GET /api/v1/files/{id}/content`
- Поиск по имени: `GET /api/v1/files/search?filename=<exact_name>` (только точное совпадение, не substring)
- Удаление: `DELETE /api/v1/files/{id}`

## §10. Как обновляется сам регламент

Регламент выпускается по той же схеме: физический документ `H2_ARCH_GUIDE_REGLAMENT_v<N>_r<M>.md` + открытка `H2_ARCH_GUIDE_REGLAMENT_ACTIVE.md`. Правила §3, §5, §8 применяются к самому регламенту.
