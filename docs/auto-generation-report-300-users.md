## 1. Как работает генерация одной порции (1 пользователь)

Пайплайн состоит из 4 шагов, выполняется асинхронно в фоновом потоке:

```
[build_profile] → [Step 1: PLAN] → [Step 2: GENERATE] → [Step 3+4: AUDIT + FIX]
     1 сек              25 сек             10×25 сек            ~100 сек
                                    (параллельно!)
```

### Шаг 0: build_profile (1 сек)
— Собирает профиль: class_level, weak/strong/calibration topics, curator_subtopic
— Хэшируется в `cache_key` (SHA-256): одинаковые профили → один пул

### Шаг 1: PLAN — [`step1_gemini.py`](daily_tasks/pipeline/step1_gemini.py:296)
— DeepSeek V4 Pro планирует 10 слотов (позиций) с темами и уровнями
— ~25 сек, ~$0.002

### Шаг 2: GENERATE — [`step2_opus.py`](daily_tasks/pipeline/step2_opus.py:286)
— 10 параллельных вызовов DeepSeek (semaphore=10)
— Каждый генерирует условие + ответ (без решения)
— ~25 сек на все 10, ~$0.02

### Шаг 3+4: AUDIT + FIX — [`step3_gpt_audit.py`](daily_tasks/pipeline/step3_gpt_audit.py:248) + [`orchestrator.py`](daily_tasks/pipeline/orchestrator.py:246)
— 10 батчей аудита (по 1 задаче), 5 параллельных
— Аудитор проверяет: уровень сложности, wrong_answer, impossible_task, spec_mismatch
— Задачи с `needs_fix` перегенерируются (до 3 попыток, 10 параллельно)
— ~100 сек, ~$0.02

### ИТОГО: ~3 мин 37 сек, ~$0.04 за генерацию
*(Было 5:41 до оптимизации LaTeX-валидатора)*

## 2. Система кэширования (самое важное для 300 пользователей!)

### [`compute_cache_key()`](daily_tasks/services.py:804)
Ключ кэша — SHA-256 от:
- `subject` (алгебра/геометрия/...)
- `class_level` (5-11)
- `class_expected_level` (1-8)
- `weak_topics` + `strong_topics` (нормализованные, отсортированные)
- `calibration_topics`
- `profile_completeness` (квантована до 0.1)

→ **Группа учеников с одинаковым профилем = 1 AI-генерация на всех**

### [`TaskPool`](daily_tasks/services.py:337-454) — общий пул задач
- **TTL**: 30 дней для `ready`, 7 дней для `partial`
- При cache HIT: задачи берутся из пула, `used_count++`
- Ротация: `_select_best_task_indices()` с rotation по `used_count`
- **Relaxed fallback**: если нет точного ключа → ищет любой пул того же grade+subject

### Сценарий кэширования:
```
Пользователь 1 (9 класс, алгебра, слаб: функции) → AI генерация (~$0.04)
Пользователь 2 (9 класс, алгебра, слаб: функции) → CACHE HIT ($0)
Пользователь 3 (9 класс, алгебра, слаб: уравнения) → AI генерация (~$0.04)
Пользователь 4 (9 класс, алгебра, слаб: уравнения) → CACHE HIT ($0)
...
```

При 300 пользователях с 7 классами × 2 предмета × ~5 комбинаций тем:
**~70 уникальных ключей → ~70 AI-генераций = ~$2.80 в месяц**

## 3. Предгенерация на завтра (PreGenQueue)

### [`_enqueue_tomorrow_pregen()`](daily_tasks/services.py:1952)
После успешной генерации сегодняшнего сета — автоматически ставит в очередь генерацию на завтра.

### Квоты:
- **`MAX_CONCURRENT_PREGEN = 2`** — только 2 одновременные предгенерации!
- **`PREGEN_SLOT_HOURS = 24`** — если очередь переполнена, запись ждёт 24 часа
- **`PREGEN_POOL_TTL_HOURS = 12`** — время жизни пула

### [`_process_pregen_queue()`](daily_tasks/services.py:2094)
Вызывается cron'ом (раз в N минут). Берёт `queued` записи с наступившим `release_at` и запускает генерацию (не более 2 одновременно).

### Проблема: 2 слота для 300 пользователей — катастрофа!
При загрузке в 8:00 UTC (11:00 МСК) 300 пользователей одновременно запрашивают задачи:
- Первые 2 получают предгенерацию (если повезло)
- Остальные 298 запускают AI-генерацию в реальном времени
- Каждая генерация = отдельный поток + 10 параллельных API-вызовов
- **300 × 10 = 3000 одновременных запросов к DeepSeek**
- Рейт-лимит DeepSeek, скорее всего, заблокирует

## 4. Банк задач vs LLM-генерация

### [`_try_bank_first()`](daily_tasks/services.py:992)
Перед запуском LLM проверяется банк готовых задач (`task_bank`):
- Только если curator_subtopic задан (кураторский цикл)
- Детерминированный день: `(today - started_at).days % 100`
- Если банк HIT → 0 затрат, мгновенная выдача

### Ручная перегенерация (`skip_bank=True`)
- Кнопка «Перегенерировать» всегда запускает полный LLM-пайплайн
- Банк не используется
- Всегда ~$0.04 на генерацию

## 6. Узкие места при 300 пользователях

### 🔴 Критическое: MAX_CONCURRENT_PREGEN = 2
2 слота на 300 пользователей. Нужно минимум 20-30.

### 🔴 Критическое: фоновая генерация по требованию
Каждый cache MISS запускает `threading.Thread` + 10 параллельных API-вызовов.
При 300 пользователях = потенциально 300 потоков + 3000 HTTP-запросов к DeepSeek.

### 🟡 Среднее: нет рейт-лимитера для DeepSeek
10 параллельных вызовов на пользователя × N пользователей = лавина запросов.

### 🟡 Среднее: PREGEN_SLOT_HOURS = 24
Если очередь переполнена — запись ждёт СУТКИ. Для пользователя это означает отсутствие задач.

### 🟢 Хорошо: кэширование
При повторяющихся профилях — экономия ~98% затрат.

## 7. Рекомендации для масштабирования

### 1. Увеличить MAX_CONCURRENT_PREGEN до 20-30
```python
MAX_CONCURRENT_PREGEN = 20  # было 2
```

### 2. Запускать предгенерацию НОЧЬЮ для всех активных пользователей
Cron в 4:00 МСК: для каждого уникального cache_key → 1 генерация в пул.
К утру все пулы готовы, пользователи получают cache HIT.

### 3. Rate-limiter для DeepSeek API
Глобальный семафор на 10-20 одновременных запросов:
```python
_GLOBAL_DEEPSEEK_SEMAPHORE = asyncio.Semaphore(15)
```

### 4. Пул потоков вместо неограниченных Thread'ов
```python
_GENERATION_EXECUTOR = ThreadPoolExecutor(max_workers=8)
```

### 5. Уменьшить PREGEN_SLOT_HOURS до 1-2
```python
PREGEN_SLOT_HOURS = 2  # было 24
```

## 8. Оценка затрат: 300 пользователей / 30 дней

### Без оптимизаций (текущее состояние):
- ~70 уникальных профилей × $0.04 × 30 дней = **~$84/мес**
- + ручные перегенерации (~10% пользователей) = +$12
- **Итого: ~$96/мес**

### С оптимизациями (ночная предгенерация):
- 70 уникальных профилей × $0.04 × 1 раз (кэш на 30 дней) = **~$2.80/мес**
- + ручные перегенерации = +$12
- **Итого: ~$15/мес**

### Разница: экономия ~$81/мес (85%) за счёт кэширования.
