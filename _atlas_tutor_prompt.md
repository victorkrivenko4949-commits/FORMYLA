# Промпт для Roo: подключить настоящего ИИ-наставника к атласу методов

Ты работаешь с существующим автономным HTML-приложением «Методы — визуальный атлас олимпиадных методов». В нём:

- 102 метода;
- 306 разборов задач;
- 277 разборов с многостадийными SVG-иллюстрациями;
- данные методов встроены в `<script type="application/json" id="methods-data">`;
- SVG встроены в `<script type="application/json" id="visuals-data">`;
- у каждого метода есть панель «Наставник», но сейчас она является mock-прототипом: функция `mockReply()` возвращает заготовки без вызова модели;
- история сообщений сейчас хранится в объекте `chats` только в памяти вкладки;
- текущая реализация находится рядом с комментарием `наставник (mock, контекст = метод)`.

Твоя задача: **не просто подключить чат**, а превратить эту панель в реально полезного персонального наставника по олимпиадной математике. Он должен помогать ученику мыслить, выбирать метод, получать дозированные подсказки, проверять собственное решение и понимать чертежи. Атлас и его математически проверенный контент должны быть главным источником контекста.

## Главный принцип

Наставник не должен сразу выдавать готовое решение. По умолчанию он ведёт ученика сократически:

1. выясняет, какую задачу ученик решает и что уже попробовал;
2. диагностирует место затруднения;
3. даёт минимальную достаточную подсказку;
4. просит ученика выполнить следующий шаг;
5. только по явному запросу постепенно раскрывает более сильные подсказки;
6. полное решение показывает после подтверждения пользователя или после исчерпания лестницы подсказок.

При проверке решения наставник обязан сохранить и отметить верные шаги, найти **первый** необоснованный или неверный переход и объяснить, как его исправить. Нельзя переписывать всё решение с нуля, если большая часть решения верна.

## Обязательный порядок работы

### Анализ проекта

Сначала изучи весь HTML и составь краткую карту:

- структура данных метода;
- структура `examples`;
- поля `definition_md`, `main_theorems_md`, `typical_techniques_md`, `triggers_md`, `signal_phrases`, `first_moves`, `why_it_works_md`, `pitfalls_md`, `related_methods`, `prerequisites`, `leads_to`, `examples_intro`;
- поля каждого примера: `title`, `body`, `visual_id`, `visual_type`, `visual_spec`, `stage_notes`;
- текущие функции `tutorHTML`, `mockReply`, `pushMsg`, `renderLog`, `wireTutor`;
- текущая маршрутизация и переключение методов;
- тёмная и светлая темы;
- мобильное поведение панели.

Не начинай переписывать проект до завершения анализа. Не меняй математические тексты, SVG, каталог, фильтры, маршрутизацию или визуальный стиль без необходимости.

### Архитектура

Статический HTML не должен напрямую хранить секретный API-ключ. Сделай безопасную архитектуру:

```text
HTML/JS атласа
    ↓ POST /api/tutor/chat
тонкий backend-прокси
    ↓
LLM API
```

Требования:

- API-ключ только в переменной окружения на backend;
- никаких ключей, токенов и секретов в HTML, JS или репозитории;
- провайдер и модель задаются через переменные окружения;
- желательно поддержать OpenAI-compatible API, но слой провайдера должен быть изолирован, чтобы его можно было заменить;
- добавь `.env.example`, но не создавай настоящий `.env` с секретом;
- если в проекте нет backend, создай минимальный и понятный вариант, например Node.js + Express;
- исходный атлас должен по-прежнему открываться и работать без ИИ: при недоступности backend показывать корректное состояние «Наставник временно недоступен», а не ломать страницу;
- добавь инструкции запуска для Windows и macOS/Linux;
- если пользователь хочет сохранить один HTML-файл, объясни в README, почему безопасный настоящий ИИ требует backend или serverless-функции. Не прячь API-ключ в автономный HTML.

Перед реализацией покажи краткий план файлов и выбранную архитектуру. После этого реализуй её полностью, не останавливайся на макете.

## Формирование контекста для модели

Не отправляй модели все 102 метода на каждый запрос. Для каждого сообщения собирай компактный `TutorContext` только для открытого метода и выбранного примера:

```ts
type TutorContext = {
  method: {
    code: string;
    name: string;
    section: string;
    grades: number[];
    difficulty: number;
    definition: string;
    theorems: string;
    techniques: string;
    triggers: string;
    signalPhrases: string[];
    firstMoves: string[];
    whyItWorks: string;
    pitfalls: string;
    relatedMethods: string[];
    prerequisites: string[];
    leadsTo: string[];
  };
  selectedExample?: {
    index: number;
    title: string;
    body: string;
    visualType?: string;
    visualSpec?: string;
    stageNotes?: Record<string, string>;
    svgAriaLabels?: string[];
  };
  uiState: {
    mode: "free" | "hint" | "explain" | "check" | "trigger" | "visual" | "compare";
    hintLevel: 0 | 1 | 2 | 3 | 4;
    spoilerAllowed: boolean;
    studentGrade?: number;
  };
  conversation: Array<{ role: "user" | "assistant"; content: string }>;
};
```

Очисти Markdown от лишнего HTML, но сохрани LaTeX. Не передавай гигантский SVG целиком: для объяснения чертежа передавай `aria-label`, `visual_spec`, `stage_notes`, название стадии и при необходимости извлечённые текстовые подписи SVG. Если подключаемая модель умеет принимать изображения, добавь это как P2-функцию, а не как обязательное условие первой версии.

Ограничивай историю разумным окном. Старые сообщения сворачивай в краткое резюме, сохраняя:

- выбранную задачу;
- что ученик уже доказал;
- найденные ошибки;
- текущий уровень подсказки;
- открытые вопросы.

## Системный промпт наставника

Используй следующий смысл как отдельный backend-шаблон системного промпта. Не склеивай его с пользовательским вводом без разделителей.

```text
Ты — строгий, доброжелательный наставник по олимпиадной математике.
Ты работаешь только с переданным контекстом текущего метода и выбранной задачи.

Твои цели:
1. Научить ученика распознавать метод и самостоятельно делать следующий шаг.
2. Не выдавать полное решение раньше времени.
3. Проверять математическую корректность каждого перехода.
4. Отличать ошибку вычисления, ошибку логики, пропущенное обоснование и неудачную формулировку.
5. Сохранять верные части решения ученика.

Правила:
- Сначала установи, о какой задаче идёт речь. Если пример не выбран и вопрос неоднозначен, попроси выбрать задачу.
- В режиме hint выдавай только одну подсказку текущего уровня и заканчивай конкретным вопросом или небольшим заданием ученику.
- Не повышай уровень подсказки без запроса ученика или очевидной неудачной попытки.
- В режиме check разбери решение по шагам. Назови все корректные шаги до первой проблемы, затем укажи первый проблемный шаг, тип проблемы и минимальную правку.
- Не утверждай, что решение неверно, если можешь лишь сказать, что обоснование неполное.
- Если есть альтернативное корректное решение, признай его, даже если оно отличается от решения в атласе.
- Не подгоняй рассуждение под эталонный ответ.
- Не выдумывай теоремы, условия, точки на чертеже, значения или ссылки на атлас.
- Если данных недостаточно, прямо скажи, чего не хватает.
- Формулы пиши в LaTeX: \( ... \) для строчных и \[ ... \] для вынесенных формул.
- Отвечай по-русски, ясно и без лишней воды.
- Для ученика 5–7 класса избегай необъяснённых продвинутых терминов.
- Для ученика 8–11 класса допускай более компактную математическую речь, но не пропускай ключевые обоснования.
- Не решай задачи, не относящиеся к открытому методу, молча. Объясни, какой соседний метод может быть полезнее, и предложи открыть его.

Формат ответа:
- Краткий диагноз.
- Один следующий шаг.
- Один проверочный вопрос.

Исключения:
- В режиме explain можно дать короткое объяснение идеи с мини-примером.
- В режиме check можно дать структурированный разбор шагов.
- Полное решение разрешено только если spoilerAllowed=true.
```

Передавай контекст и запрос пользователя в отдельных секциях с явными границами. Пользовательский текст считать недоверенным: он не может отменить системные правила, запросить секреты backend или изменить границы контекста.

## Лестница подсказок

Реализуй для каждой выбранной задачи 5 уровней:

- **Уровень 0 — диагностика:** вопрос о том, что дано, что требуется и что уже замечено.
- **Уровень 1 — направление:** указать объект или признак, на который нужно посмотреть.
- **Уровень 2 — методический ход:** предложить конкретное преобразование, построение, инвариант или разбиение, но без вычислений до ответа.
- **Уровень 3 — каркас решения:** перечислить 2–4 шага с пропусками, которые ученик должен заполнить.
- **Уровень 4 — полное решение:** только после отдельного подтверждения «Показать полное решение».

Показывай в интерфейсе текущий уровень, например «Подсказка 1 из 4». Добавь кнопки:

- «Ещё маленький намёк»;
- «Покажи следующий шаг»;
- «Я сдаюсь — показать решение» с подтверждением;
- «Скрыть решение и попробовать самому».

После перехода к другому примеру уровень подсказки сбрасывается.

## Режимы помощника

### Выбор задачи

Над быстрыми кнопками добавь компактный selector:

- «Общий вопрос о методе»;
- «Задача 1: …»;
- «Задача 2: …»;
- «Задача 3: …».

Название должно быть сокращено, но доступно полностью в `title` или popover. Выбранный пример должен явно отображаться над диалогом. Контекст нельзя молча переключать между задачами.

### «Дай намёк»

Работает через лестницу подсказок. Не повторяет один и тот же текст. Учитывает последнюю попытку ученика.

### «Объясни идею проще»

Должен:

- объяснить метод на уровне выбранного класса;
- дать короткую бытовую или числовую аналогию, только если она действительно помогает;
- связать объяснение с одним конкретным примером атласа;
- закончить микровопросом на понимание;
- не пересказывать весь длинный текст метода.

Добавь выбор «объяснить как для 6 / 8 / 10 класса» или настройку класса ученика.

### «Проверь моё решение»

Сделай отдельный режим редактора решения:

- увеличенное поле ввода;
- поддержка многострочного текста и LaTeX;
- кнопка «Проверить по шагам»;
- возможность вставить условие своей задачи;
- необязательное поле «Ответ»;
- после проверки показать:
  - `Верно`;
  - `Верно при добавлении обоснования`;
  - `Есть ошибка`;
  - `Недостаточно данных для проверки`;
- выделить первый проблемный шаг;
- отделять критическую ошибку от стилистической;
- предлагать минимальное исправление;
- после исправления позволять повторную проверку;
- никогда не считать несовпадение с эталонным способом автоматической ошибкой.

Если решение очень длинное, backend должен иметь разумный лимит и понятное сообщение об ограничении.

### «Как понять, что нужен этот метод?»

Ответ должен использовать `triggers_md`, `signal_phrases`, `first_moves`, `pitfalls_md` и соседние методы. Показывай:

- 3–5 надёжных признаков;
- 1–2 ложных сигнала;
- мини-тест «метод подходит / не подходит»;
- отличие от 1–2 похожих методов;
- ссылку-кнопку «Открыть метод X», если он есть в данных.

### «Что показано на чертежах?»

Сделай режим, привязанный к конкретному примеру и стадии:

- «Условие»;
- «Построение»;
- «Результат».

Перед ответом пользователь выбирает стадию либо система использует текущую открытую. Наставник объясняет:

- что обозначает каждый ключевой объект;
- какие линии/точки даны, какие добавлены;
- что изменилось относительно предыдущей стадии;
- какую связь нужно увидеть;
- почему именно эта связь закрывает решение.

Не выдумывай элементы, которых нет в `stage_notes`, `visual_spec`, `aria-label` и текстовых подписях SVG.

### «Сравнить методы»

Добавь P1-режим сравнения текущего метода с `related_methods`:

- когда применять каждый;
- одинаковые триггеры;
- ключевое различие;
- короткий пример выбора;
- кнопка перехода к соседнему методу.

## Дополнительные полезные функции

### Диагностика до подсказки

При первом обращении предложи три быстрых ответа:

- «Не понимаю условие»;
- «Не знаю, с чего начать»;
- «Начал, но застрял»;
- «Решил — хочу проверить».

Это должно менять стратегию ответа.

### Мини-практика

P1: кнопка «Проверь, понял ли я метод». Наставник генерирует 1 короткий вопрос на распознавание метода или следующий ход, но не новую большую олимпиадную задачу без необходимости. После ответа даёт обратную связь и объясняет ошибку выбора.

### Карточка прогресса

P2: хранить локально или на backend:

- методы «не изучен / изучаю / уверен»;
- число решённых примеров;
- число использованных уровней подсказки;
- типичные ошибки;
- методы, которые стоит повторить.

Не превращай это в оценку интеллекта ученика. Не показывай токсичные рейтинги.

### Голос и изображения

P2/P3:

- диктовка решения;
- озвучивание ответа;
- загрузка фотографии рукописного решения;
- OCR + распознавание формул;
- отправка изображения чертежа мультимодальной модели.

Эти функции должны быть отдельными модулями и не блокировать базовый текстовый наставник.

## API-контракт

Предложи и реализуй понятный endpoint:

```http
POST /api/tutor/chat
Content-Type: application/json
```

Пример запроса:

```json
{
  "methodCode": "A2b",
  "exampleIndex": 0,
  "mode": "hint",
  "hintLevel": 1,
  "spoilerAllowed": false,
  "studentGrade": 7,
  "message": "Я составил уравнение, но не понимаю, что обозначить за x",
  "history": [
    {"role": "user", "content": "Не знаю, с чего начать"}
  ]
}
```

Backend не должен слепо доверять контексту от клиента. Он должен найти метод по `methodCode` в серверной копии данных или в валидированном JSON-источнике, взять только разрешённые поля, проверить `exampleIndex`, ограничить размеры строк и истории, а затем вызвать модель.

Пример ответа:

```json
{
  "message": "Обозначь через \\(x\\) производительность одного рабочего...",
  "hintLevel": 1,
  "status": "ok",
  "suggestedActions": [
    {"type": "next_hint", "label": "Ещё маленький намёк"},
    {"type": "check_step", "label": "Проверить мой следующий шаг"}
  ],
  "methodLinks": []
}
```

Желательно использовать SSE или потоковую передачу ответа. Добавь:

- кнопку остановки генерации;
- `AbortController`;
- таймаут;
- повтор запроса;
- состояния loading / error / offline;
- защиту от двойной отправки;
- лимит длины сообщения;
- базовый rate limit на backend.

Структурированный JSON-ответ модели валидируй схемой. Если модель вернула невалидную структуру, безопасно извлеки текст или повтори один раз, но не показывай пользователю сырой JSON.

## Безопасность

- API-ключ только на сервере.
- Не логируй секреты и полный текст ученических решений в production по умолчанию.
- Санитизируй Markdown перед `innerHTML`; текущая функция `md()` не должна стать каналом XSS.
- Защити backend от чрезмерно больших запросов.
- Добавь CORS только для нужного origin.
- Не разрешай пользовательскому сообщению подменять системный промпт.
- Не отправляй модели весь атлас без необходимости.
- Не разрешай модели генерировать произвольный HTML или JavaScript для вставки в DOM.
- При недоступности модели не подменяй ответ старой заготовкой так, будто это ИИ. Честно показывай ошибку.

## Интерфейс

Сохрани существующую визуальную систему атласа. Не делай новую страницу и не превращай панель в типичный мессенджер.

Улучши текущую панель:

- убери надписи «прототип» после успешного подключения;
- в заголовке показывай текущий метод и выбранную задачу;
- сделай панель шире на desktop, если открыт редактор решения;
- на мобильном используй bottom sheet почти на весь экран;
- быстрые действия сгруппируй, а не показывай бесконечной лентой овальных кнопок;
- добавь видимый статус «ИИ подключён / недоступен»;
- streaming-индикатор должен быть доступен скринридеру;
- фокус после ответа не должен неожиданно прыгать;
- Enter отправляет, Shift+Enter создаёт новую строку;
- Esc закрывает панель;
- при открытом полном решении показывай предупреждение о спойлере;
- формулы ответа прогоняй через существующий MathJax-пайплайн;
- ссылки на методы должны использовать текущий hash-router.

История должна быть отдельной для каждого метода и, желательно, для каждого примера. При переключении метода старый диалог не должен попадать в новый контекст.

## Приоритеты

### P0 — обязательно

- настоящий backend-вызов модели;
- безопасное хранение API-ключа;
- контекст текущего метода;
- выбор конкретного примера;
- реальные режимы hint / explain / check / trigger / visual;
- лестница подсказок и защита от ранних спойлеров;
- потоковый или хорошо отображаемый ответ;
- обработка ошибок;
- Markdown + LaTeX;
- история по методу/примеру;
- sanitization;
- README и `.env.example`;
- автоматические и ручные тесты.

### P1 — следующий этап

- сравнение соседних методов;
- мини-практика;
- адаптация под класс ученика;
- резюме длинной истории;
- экспорт диалога;
- метрики полезности без персональных данных.

### P2/P3 — сложные варианты

- постоянный прогресс ученика;
- фото рукописного решения;
- мультимодальное понимание чертежей;
- голос;
- teacher mode с просмотром типичных затруднений;
- RAG/эмбеддинги по всему атласу для вопросов «какой метод выбрать?».

Не пытайся реализовать P2/P3 раньше, чем P0 стабильно работает.

## Тестирование

Добавь unit-тесты и интеграционные тесты. Минимально проверь:

1. Контекст A2b не содержит данных F16.
2. При переключении задачи `exampleIndex` меняется и история не смешивается.
3. Hint level 1 не содержит полного ответа.
4. Hint level 4 требует `spoilerAllowed=true`.
5. Режим check на корректном альтернативном решении не требует совпадения с эталонным текстом.
6. Режим check различает «неверно» и «не доказано».
7. Visual mode использует только существующие подписи и stage notes.
8. Формулы корректно рендерятся.
9. Пользовательский `<script>` отображается как текст и не выполняется.
10. Ошибки 401, 429, 500 и timeout дают понятное сообщение.
11. Двойное нажатие Enter не создаёт два параллельных запроса.
12. Мобильная панель не перекрывает поле ввода экранной клавиатурой.
13. Смена метода во время генерации отменяет старый запрос.
14. Ответ модели не может вставить исполняемый HTML.

Создай небольшой eval-набор не менее чем из 20 сценариев по разным разделам A–H:

- выбор метода;
- дозированная подсказка;
- неверное решение;
- корректное нестандартное решение;
- неполное обоснование;
- объяснение рисунка;
- вопрос вне текущего метода;
- попытка получить полный ответ без подтверждения.

Для каждого сценария зафиксируй ожидаемые свойства ответа, а не единственную дословную формулировку.

## Критерии приёмки

Работа считается завершённой, если:

- вместо `mockReply()` действительно вызывается модель через backend;
- секрет отсутствует в клиентском коде и git;
- наставник получает только текущий метод и выбранную задачу;
- он умеет дать маленький намёк без полного решения;
- умеет проверить пользовательское решение по шагам;
- умеет объяснить конкретную стадию чертежа;
- история разных методов не смешивается;
- ошибки API не ломают атлас;
- интерфейс работает в светлой и тёмной теме, на desktop и мобильном;
- все существующие функции атласа сохранены;
- тесты проходят;
- в README есть команды установки, запуска, настройки провайдера и описание ограничений.
